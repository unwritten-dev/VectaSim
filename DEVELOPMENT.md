# VectaSim – Development

Technical documentation for everyone working on the code. The user’s view is in the [README](README.md) (German: [README.de.md](README.de.md)) and in [docs/installation.md](docs/installation.md); both deliberately stay free of development details. Releases: [docs/releasing.md](docs/releasing.md); first test against real MSFS/X-Plane: [docs/sim-pc-checklist.md](docs/sim-pc-checklist.md).

## Stack

- **Desktop shell:** Tauri v2 (Rust backend, WebView2 frontend), Windows first.
- **Frontend:** React 19 + TypeScript, Vite, MapLibre GL JS 6, Vitest. No UI library – own components in `app/src/ui/`, design tokens as CSS variables, six switchable themes in `app/src/themes.ts`.
- **Backend:** Rust workspace, SQLite 3.53.2 (rusqlite 0.40, bundled; the test `bundled_sqlite_is_new_enough` requires ≥ 3.50.2), reqwest (rustls).

## Prerequisites

- Rust via `rustup` (MSVC target), Visual Studio Build Tools 2022 with the C++ workload, WebView2 (included in Windows 10/11). The compiler version is pinned in `rust-toolchain.toml` (currently 1.99.1); `rustup` installs it by itself on the first `cargo` call in the repo. To bump it: change the file + run Clippy.
- Node.js 22
- For real sim data, a `SimConnect.dll` (search order see `docs/installation.md`, origin see “SimConnect.dll” below); without a sim, everything runs against the mock – which never loads the DLL.

## Developing

```bash
cd app && npm ci
```

Mock flight (no simulator; flies a circuit at EDDF 25C with a clean 3° approach; `VECTASIM_MOCK=bounce` for a bounced landing, `VECTASIM_MOCK=goaround` for a go-around at 300 ft with a second circuit):

cmd:

```bat
cd app && set "VECTASIM_PROVIDER=mock" && npm run tauri dev
```

PowerShell:

```powershell
cd app; $env:VECTASIM_PROVIDER="mock"; npm run tauri dev
```

With a simulator: `npm run tauri dev` without the variable. Dev logs with `RUST_LOG=info`.

Simulator selection: without a variable, *Settings → Simulator* applies (default `auto`: SimConnect first, X-Plane if no MSFS is there for 10 s or the DLL is missing and an X-Plane Web API responds; logic in `app/src-tauri/src/simselect.rs`). `VECTASIM_PROVIDER=simconnect|xplane|auto|sim|mock|replay` fixes it for the run; X-Plane endpoint `VECTASIM_XPLANE_HOST` / `VECTASIM_XPLANE_PORT` (default `localhost:8086`).

**X-Plane provider** (`crates/vectasim-xplane`): `GET /api/capabilities` (version, API v2 preferred) → `GET /api/v2/datarefs?filter[name]=…` (IDs) → WebSocket `/api/v2`, one `dataref_subscribe_values` per dataref (otherwise one failed subscription would take down all datarefs of its request) → `dataref_update_values` at 10 Hz, changed values only. Numeric datarefs are kept as a fixed slot list (arrays: element 0…n−1); that is also the raw format in the `.vsdump` (`source: "xplane"`, `data` with `req` 1, `null` = not in this message; strings `req` 3). Tests run against a fake Web API server (`src/tests.rs`, fixture `tests/fixtures/webapi-session.json`); the replay (`vectasim_simconnect::replay::AnyPlayer`) picks the decoder by `source`.


Result: `target\release\bundle\nsis\VectaSim_<version>_x64-setup.exe` (relative to the repo root, not to `app/`). An installer built this way works normally; only the auto-update signature is missing.

The installer includes `app/src-tauri/windows/hooks.nsi` (`bundle.windows.nsis.installerHooks`; macros `NSIS_HOOK_POSTINSTALL` etc. from Tauri’s `installer.nsi`; the generated version is under `target\release\nsis\x64\` after the build). The file must stay UTF-8 **with BOM**, otherwise `makensis` reads the umlauts as ANSI. Silent test: `VectaSim_<version>_x64-setup.exe /S` (installs per user to `%LOCALAPPDATA%\VectaSim\`, asks nothing and downloads no DLL); passive like the updater: `/P`. The SimConnect question only appears in the normal, interactive installation.

### Raw dump, replay and probe tool (reproducing errors from the sim PC)

**Recording (sim PC):** *Settings → Diagnostics → Record raw dump* writes one `%LOCALAPPDATA%\io.vectasim.app\dumps\<YYYYMMDD-hhmmssZ>.vsdump` per SimConnect session (next to `logs\`). Regardless of the switch, the app keeps the last 30 min in RAM (≤ 64 MB, in practice ≈ 4 MB); *Save dump now* writes them as `dumps\ring-<time>.vsdump`. Recording happens in the SimConnect session dispatch **before** any interpretation – so decoder errors (units, indices, BCD) stay reproducible.

**Format `.vsdump`** (version 1; details in `crates/vectasim-dump/src/lib.rs`): zstd-compressed NDJSON (also several concatenated zstd frames; uncompressed NDJSON is read as well).

- Line 1 `{"type":"header","format":1,"app",…,"source":"simconnect","sim","simVersion","simconnect","dll","defs":{"fast":[[name,unit]…],"slow":[…],"static":[…],"approach":[…],"design":[…]},"reqs":{"approach":4,"design":5,"fast":1,"slow":2,"static":3},"inactive":{…},"startedWallMs"}`
- Definitions: `fast` (SIM_FRAME), `slow` (1 Hz), `static` (strings, once per aircraft), `approach` (1 Hz, track v2: `AMBIENT WIND VELOCITY/DIRECTION`, `NAV HAS LOCALIZER/HAS GLIDE SLOPE/GS FLAG/GLIDE SLOPE ERROR/CDI/RADIAL ERROR/RAW GLIDE SLOPE/LOCALIZER:1`, `AUTOPILOT MASTER/APPROACH HOLD/GLIDESLOPE HOLD/MANAGED THROTTLE ACTIVE/THROTTLE ARM`, `TURB ENG N1:1..2`, `GENERAL ENG THROTTLE LEVER POSITION:1`, `SPOILERS HANDLE POSITION/ARMED/LEFT POSITION`, `INCIDENCE ALPHA`, `FLAPS NUM HANDLE POSITIONS`) and `design` (once per aircraft, again after `AircraftLoaded`: `DESIGN SPEED VS0/VS1` in kt, `VC` requested in ft/s and converted). `approach`/`design` are additive (still format 1): older dumps don’t have them and play back unchanged (fields `None`), older builds ignore them. A rejected variable only drops out of its own definition; in `approach` it then reads `None` (not “last value”). ILS deviations only count while the station has the component (`NAV HAS LOCALIZER/GLIDE SLOPE`).
- After that, one `{"t":<ms monotonic>,"w":<wall clock ms>,"k":…}` per message with `k` = `data` (`req` + `v` raw f64 or `s` strings; NaN → `null`), `event` (`id` = name, `data`), `filename` (`id`, `path`), `exception` (`code`, `sendId`, `index`, mapped `call`/`def`/`var`, `dropped`), `open` (sim and SimConnect version), `quit`, `hr` (`fn`, `hr`), `systemState` (`req`, `int`), `end` (`reason` of the session).
- Compaction: between keyframes, a `dv` replaces `v` – the difference of the IEEE 754 bit patterns to the previous `data` of the same `req` (lossless). A keyframe at the start of every file/ring chunk and at least once per second. The reader always returns `v`. Result: 60 Hz × 17 FAST values ≈ 7–8 MB/h (test `sixty_hz_fast_stays_below_10_mb_per_hour`).
- A truncated file (app closed) is readable up to the last second (flush once per second).

**Playback (dev PC):** copy the dump file from the sim PC, then

```powershell
cd app; $env:VECTASIM_PROVIDER="replay"; $env:VECTASIM_REPLAY="C:\path\20261017-140322Z.vsdump"; $env:VECTASIM_REPLAY_SPEED="10"; npm run tauri dev
```

```bat
cd app && set "VECTASIM_PROVIDER=replay" && set "VECTASIM_REPLAY=C:\path\20261017-140322Z.vsdump" && set "VECTASIM_REPLAY_SPEED=10" && npm run tauri dev
```

`VECTASIM_REPLAY_SPEED`: default `1`, `0` = as fast as possible; `VECTASIM_REPLAY_LOOP=1` repeats. Short form `VECTASIM_PROVIDER=replay:<file>`. Alternatively, in the running app *Settings → Diagnostics → Replay*: choose a file, speed, *Start replay*/*Stop replay* (back to SimConnect). The replay provider sends `Connected { sim_name: "Replay <file>" }` and feeds the lines through **the same decoder** as the live session (`crates/vectasim-simconnect/src/decoder.rs`); if the dump’s definitions no longer match the build, values are mapped by SimVar name. Time: `Telemetry.timestamp_ms = start + (t − t₀)` in *recorded* milliseconds, playback pace `(t − t₀)/speed` – so the engine sees exactly the recorded timeline (dwells behave as live, they just run ten times faster at factor 10). Start = wall clock at replay start; with `0`, the recorded wall clock (deterministic, for tests). Replay flights land in the logbook with provider `replay`.

**Creating a dump without a sim:** `cargo run -p vectasim-simconnect --example mock-to-vsdump -- out.vsdump [--variant bounce] [--from 0] [--to 600] [--hz 60]` (mock flight → raw values, inverting the decoder conversions). Without options, this produces the fixture `crates/vectasim-core/tests/fixtures/mock-circuit.vsdump` (60 s of final approach + landing + 20 s of rollout, full 60 Hz); the test `the_fixture_is_what_the_generator_produces` reports when it needs to be regenerated. Trimmed dumps from the sim day go into the same folder, with a golden test next to them (`replay::replay_file` returns the `ProviderEvent`s with a simulated clock).

**Live raw data:** *Settings → Diagnostics → Live raw data* (collapsed) shows every definition (FAST/SLOW/STATIC) with SimVar, unit, raw value, converted value, age and rate per request, the last 100 events/exceptions with name and mapped SimVar, the engine internals (`FlightSession::debug_state`) and connection info. Data path: command `diagnostics_snapshot` + event `diag:raw` (2 Hz, only while the view is open: `set_diag_stream`). Mock: no raw definitions (“–”).

**Probe tool** (Windows only, not bundled): connects with the same definitions and the same session code as the app, writes raw values once per second plus every event, every exception and every log line to the console and to `probe.log`, optionally a dump:

```powershell
cargo build -p vectasim-simconnect --bin vectasim-probe --release
target\release\vectasim-probe.exe --dump probe.vsdump --log probe.log [--index 0] [--seconds 600]
```

If the app breaks on the sim PC, the probe shows whether the problem is in SimConnect or in the app logic; its dump can be played back like any other.

### Tests and checks

```bash
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cd app && npm run lint && npx tsc --noEmit && npm test
node scripts/readme-pair-check.mjs
node scripts/third-party-licenses.mjs --check
```

CI (`.github/workflows/ci.yml`) runs these steps on every push to `main` and every pull request (the Windows `rust` job only in the public repository, for tags, or on `workflow_dispatch` – private Windows minutes count double and the same checks run locally before every commit), Cargo with `--locked` (an outdated `Cargo.lock` fails the run, as does `npm ci` with an outdated `package-lock.json`), plus:

- `cargo audit` against the RustSec database (vulnerabilities fail the job, “unmaintained” notices are only printed); an accepted advisory would go into `.cargo/audit.toml` with its ID and the reason – the list is empty, and an entry is removed as soon as the dependency is fixed,
- `cargo deny --locked check` with the rules in `deny.toml` (locally: `cargo install cargo-deny --locked`, then the same command). It checks the dependency graph of the Windows build (`x86_64-pc-windows-msvc`, the one the installer ships and THIRD-PARTY-NOTICES.md lists). Advisories: vulnerabilities, yanked and unsound crates always fail, “unmaintained” only for direct dependencies, `ignore = []` (an entry needs `id` and `reason`). Licences: only the allowlist, which matches the licences in THIRD-PARTY-NOTICES.md – a new licence goes into the notices first. Bans: wildcard versions fail, several majors of one crate (Tauri brings some) only warn. Sources: crates.io only, no git dependencies,
- `npm audit --omit=dev --audit-level=high`: high or critical advisories in the production dependencies – what ends up in the installer – fail the job; dev tooling (Vite, ESLint, Vitest) never reaches users and is not audited there, so a dev-only advisory cannot block a fix release,
- `scripts/third-party-licenses.mjs --check` (locally and in the snapshot script, not in CI yet): `THIRD-PARTY-LICENSES.txt`, which the installer ships, records a fingerprint of the dependency set (registry packages of `Cargo.lock`, non-dev packages of `app/package-lock.json`, name and version); the check fails when the lock files no longer match it. Without `--check` the script regenerates the file: `cargo about generate` (cargo-about 0.9.2, pinned; `cargo install cargo-about --locked --version 0.9.2 --features cli`; offline, with `scripts/third-party-licenses/about.toml` – the same Windows graph as `deny.toml`, normal dependencies only – and the template `about.hbs`), `npx license-checker-rseidelsohn@5.0.1 --production --json` in `app/` (the licence file of each package; the `@tauri-apps` plugins only ship an SPDX manifest, so their copyright line comes from there with the MIT text), and the hand-written `scripts/third-party-licenses/data-licenses.txt` for the embedded data. A VectaSim version bump alone does not change the fingerprint.
- `scripts/readme-pair-check.mjs`: README.md and README.de.md must have the same headings, list items, table rows, images and code blocks in the same order, and every relative link and in-page anchor must resolve. Prose is not compared – a changed sentence still has to be changed in both files by hand.

The release workflow runs the same jobs on the tagged commit (`workflow_call`) in parallel with the build; publish the draft only from a green run. All actions are pinned to commit SHAs.

Tools:

### Notes from the third audit wave (0.6.3)

- Phase engine: Pushback with the parking brake set, engines off and GS < 1 kt for 30 s goes back to **Preflight** (the flight stays open with its off-block); Preflight parked like that for a further 15 min goes to Shutdown and the flight ends as a discarded ground session. `Telemetry::placeholder_position()` (|lat|, |lon| < 0.01°, the MSFS load placeholder) is ignored by the session, the recorder and the resume check; a flight started in the air is "flown" only after 3 s of movement.
- Statistics rule (`counts_in_stats`, SQL and `FlightRow`, mirrored in `app/src/flightStats.ts`): a flight that ended in an airborne phase counts only from `AIRBORNE_ONLY_MIN_DISTANCE_NM` (1 nm) on.
- `airframe.rs`: `invalidate_airframe_results` / `invalidate_flight_results` drop approach facts and flight metrics on every path that changes the assessment profile (Vapp, flaps, profile, ICAO type, rebook/unbook, merge, delete, custom-profile delete); the app emits `approach:facts` and `flight:metrics` afterwards (`results_invalidated()`).
- Recorder: a failed flight start/end is retried with an exponential backoff (1 s … 60 s, logged at most once a minute); `take_closed()` hands out flights whose end was actually written (never discarded ones) – the manager computes the approach facts from that list, not from `FlightEnded`.
- Resource figures in the README ("Resource usage"): `scripts/measure-resources.ps1 -Label … -Seconds 30` against the release build (`npx tauri build --no-bundle` in app/, then `target\release\vectasim.exe` with `VECTASIM_PROVIDER=mock`), one run per state (idle logbook, idle map with traffic, 2D following, 3D + traffic, minimised); it sums private memory, working set and CPU over the app and its WebView2 processes. Re-measure for releases that change the map or the recorder and update both READMEs.
- Results epoch: `Store::results_epoch` / `put_flight_results` / `results_changed` – every invalidation path raises the counter before it changes the cache, and a result computed with older inputs is not stored (recomputed on the next read). `flight_results_fresh` / `store_facts_unless_fresh` keep the inline path and the backfill from analysing the same flight twice. The low hop out of a take-off roll ends Takeoff → Landing (a real flight). The recorder's flush interval is 15 s up to 2 h of track, 30 s up to 6 h, 60 s beyond. KML follows the backend language.
- X-Plane nav data (`crates/vectasim-route/src/xplane.rs`): 4 KB per line, 8 airway names per segment, 2 M index entries (a file beyond that is dropped whole); UNC install paths are skipped.
- Frontend: a flight's assessment can change without the flight changing. `app/src/landing/approachChanges.ts` (`watchApproachChanges` / `useApproachRevision`) folds `approach:facts`, `approach:profiles` and `flight:metrics` into one debounced reload for the shown flight; the runway correction has no backend event, so `RunwayEditor` signals it in the window with `notifyApproachDataChanged()`.

## Architecture in brief

- **Provider → channel → forwarder.** Every sim provider runs on its own thread and pushes `ProviderEvent`s (telemetry at native rate, aircraft, sim events, status). The `ProviderManager` (`app/src-tauri/src/manager.rs`) keeps one `FlightSession` and one `FlightRecorder` per connection, throttles telemetry for the webview to 10 Hz (hidden window: 1 Hz, see “Performance”) and emits `sim:*` events.
- **Flight phases** (`crates/vectasim-core/src/phase.rs`): 12 phases, time-based hysteresis, samples during pause/slew/time acceleration are ignored; “on the ground” only if AGL ≤ 50 ft (or GS ≤ 200 kt without AGL) – the thresholds are in the file header.
- **Time base** (`crates/vectasim-core/src/clock.rs`): `Telemetry.timestamp_ms` stays wall clock (display, logbook, track). Phase dwells, touchdown windows, pauses and distance integration run on a monotonic clock (`MonoClock`): if the system clock jumps back, that counts as Δt = 0 (`clock_jump` in the log, `clockJumps` in the debug state) instead of stalling phase detection until the clock reaches the old value again. Time acceleration (sim rate ≠ 1) is treated the same way in the phase engine and the touchdown detector: both skip those samples; a landing made under time acceleration appears in both at the first real-time sample on the ground (rate then from the sim value), and the flight carries `time_acceleration_detected`.
- **Touchdown** (`touchdown.rs`): ring buffer on the full stream; landing rate = sim value (`PLANE TOUCHDOWN NORMAL VELOCITY` × 60) with a fallback to the last airborne vertical speed, worst of bounces within one event, debounce over several ground samples, first contact as time/position. Touch-and-gos are stored but never count as the flight’s landing.
- **Approach rating** (`crates/vectasim-core/src/approach.rs`): pure functions over track (1 Hz) + phases + touchdowns + runway candidates; finds approach attempts including go-arounds, assigns the runway even without a touchdown, rates gates (10 nm, FAF proxy, 1000, 500, 50 ft) and continuous criteria (EASA two-stage with minimum duration, outliers < 3 s don’t count) and returns “stable from”, bands, stability measures, lateral tracking (`lateral`: its own band by VectaSim convention; not rated with a derived runway via `apply_runway_geometry`), energy proxy. Results per approach in `approach_facts` (schema 8, versioned, lazy + at flight end). **Stage 2 (track v2, everything `Option`):** the simulator’s ILS becomes the reference if the glide slope was valid for ≥ `ils_min_share` (60 %) of the samples 1000 → 200 ft (`HAS_GLIDE_SLOPE` + `GLIDE_SLOPE_VALID`) and the median deviation from the geometry is ≤ `ils_reject_gs_deg` (otherwise “foreign ILS”, geometric); angle from `gs_angle_deg`, dots from `gs_error_deg / gs_dot_deg` or `−loc_cdi / 127 × loc_full_scale_dots`. Geometry and sim are always both computed (`ApproachProfilePoint::gs_dots_sim/geo`, `loc_dots_sim/geo`, metrics in `IlsStats`); `ApproachReference::glidepath_source`/`localizer_source` says what the criteria use. In addition `WindStats` (sim wind 1000 → 50 ft), the criteria `LandingFlaps` (gate; `AircraftRef::landing_flaps_index` from the airframe → `flap_positions − 1` → setting at touchdown), `Thrust` (N1, only if anywhere > `n1_valid_min_pct`) and `Spoilers` (both also as continuous specs with minimum duration), `EnergyBand` 10 nm → 1000 ft on final, `AutomationStats` (informational only) and the Vapp cascade user → flown → `Design` (VS0 × 1.3). VS0 and flap positions come from the track via `app/src-tauri/src/approach.rs`, Vapp/landing flaps from the airframe (`Store::flight_airframe_refs`). v1 tracks (`nav_recorded` false, no N1/wind values) fall back exactly to stage 1. Tests: `crates/vectasim-core/tests/approach_tests.rs` (v2 mock standard/go-around, synthetic approaches with/without ILS, foreign ILS, wind, thrust, spoilers, cascade, profiles), frontend `app/src/landing/approachStage2.test.tsx`; approach card `ApproachCard.tsx` + `exportApproachCard.ts` (autosave in `autoSaveCard`).
- **Assessment profiles** (`crates/vectasim-core/src/approach_profile.rs`, user documentation `docs/approach-profiles.md`, sources `docs/approach-profiles-sources.md`): a profile is an id, a name and the `ApproachConfig` keys that differ (`overrides`, camelCase, table `OVERRIDE_KEYS` with the allowed ranges); `ApproachProfile::config()` lays them over `ApproachConfig::default()` (a custom profile over its `basedOn` built-in first) and sets `profile_id`. Built-ins as a const table with a source row per value: `generic` (= default), `airbus` (`gateSpeedAboveKt` 10), `boeing` (= generic), `turboprop` (`gateSpeedAboveKt` 5, `thrustCheck` false), `ga_piston` (`gateSpeedAboveKt` 10, `speedS1/S2AboveKt` 10/20, `vsS1/S2Fpm` 1000/1200, `configGateFt` 500, `hardGateFt` 300). New config fields: `profile_id`, `hard_gate_ft` (replaces the fixed 500 ft of the band logic and `Exceedance::below_500`; the gate list keeps 1000/500 ft; serialised names `unstableBelow500`/`below500` unchanged), `thrust_check`; gates above `config_gate_ft` skip gear and flaps. Resolution (`approach_profile::resolve`, `Store::resolve_flight_profile`, `approach::flight_config` in the app): airframe choice (`airframes.approach_profile`, a deleted custom id is ignored) → ICAO type (`profile_for_type`: airframe type, else `ATC MODEL`, else the OFP type) → engine (the sim's `ENGINE TYPE` is not recorded; the app only derives "piston" from a v2 track whose N1 stays ≤ `n1_valid_min_pct` in the air) → generic. Custom profiles: setting `approach.custom_profiles` (JSON array, at most 50, file ≤ 16 KB), parsed and validated by `vectasim_store::parse_custom_profile` (unknown keys, wrong types, ranges, slug id, built-in ids reserved, S2 ≥ S1, hard gate ≤ window top; refusal `store.approach_profile_invalid` with the reason). Commands `approach_profiles`, `import_approach_profile` (path from the file dialog, `data::check_path`, `.json`), `delete_approach_profile`; event `approach:profiles`. Replacing/deleting a profile or changing an airframe's profile (or rebooking a flight onto another airframe) drops the affected `approach_facts`/`flight_metrics` rows; they are refilled by the existing lazy paths. Frontend: `landing/approachProfiles.ts` (shared list, names, value texts, tooltip), `AssessedWith.tsx`, `ApproachProfilesPanel.tsx` (Settings), the fleet dropdown in `Fleet.tsx`; `compareApproach`, the exceedance/gate metric comparisons and the trends (profile chips) only compare within one profile (a missing `profileId` counts as generic).
- **Landing analysis** (`landing.rs`): pure functions over track + touchdown + runway (OurAirports thresholds) + METAR wind: touchdown point relative to the threshold, centreline offset, touchdown zone, glide path against 3°, flare, rollout, stabilised approach gates at 1000/500 ft. The “VectaSim index” (0–100) is formed in the frontend from bands (`app/src/landing/facts.ts`, formula visible under “Methodik”, methodology).
- **Store** (`crates/vectasim-store`): SQLite in WAL mode at `%APPDATA%\io.vectasim.app\vectasim.db`, migrations in `store.rs` (`schema_version`), tracks as column-wise delta/varint + zstd (~10 bytes/sample; format in `track.rs`: **track v2** = the 16 base columns, a presence bitmask per sample and 17 optional columns – TAS, magnetic heading, sim wind, ILS deviations/angle/course, `nav_flags` (bits from `approach::nav_flags`: LOC, GS, GS valid, AP, APPR, G/S, A/THR, spoilers armed), N1, spoiler surface/lever, alpha, flap positions, VS0/VS1; **track v3** = the same layout, it only marks that pitch and bank are stored in VectaSim's convention (nose-up / right-wing-down positive) – up to 0.6.3 the SimConnect decoder stored the sim's raw sign, so `decode_track_from` negates pitch/bank of a v1/v2 blob whose flight has provider `simconnect`; the encoder always writes v3, the decoder reads v1–v3, missing values are `None`; mock circuit ≈ 8.5 bytes/sample), flush every 15 s (`FLUSH_INTERVAL_MS` in `recorder.rs`); a flight left open by a crash is marked incomplete at the next start. **Schema v17** (`MIGRATION_V17`): the landings counted into a learnt runway (`user_runway_landings`) have no foreign key to `flights`; the trigger `user_runway_landings_follow_flight` (`AFTER DELETE ON flights`) removes them together with their flight, and the migration deletes the rows that were already orphaned. A trigger instead of `REFERENCES … ON DELETE CASCADE`, because that would need a table rebuild and would refuse rows whose flight is not there yet (the `.vectasim` import writes runways before flights, in batches). Moving a flight to the trash deletes nothing, so its landings keep counting until it is deleted permanently. **Schema v18** (`metrics::MIGRATION_V18`): `flight_metrics`, one row per flight (cascade): take-off rotation (mean/peak pitch rate, duration), gear-down AGL and great-circle distance to the threshold of the landing approach's runway, landing-flaps AGL, exceedances and the 1000/500 ft gate verdicts of the landing approach, plus its runway (`None`/NULL = not determinable; a flight with nothing measurable still gets its row). Versioned like `approach_facts` (`FLIGHT_METRICS_VERSION`); dropped together with the approach facts when the runway geometry at the airport or the airframe's Vapp/landing flaps/assessment profile change, and on a merge. **Schema v19** (`MIGRATION_V19_COLUMNS`, each column only when missing): `approach_facts.profile_id`, `flight_metrics.approach_profile` (the assessment profile the results were computed with, so comparisons stay within one profile) and `airframes.approach_profile` (NULL = automatic). The results themselves are recomputed through `APPROACH_FACTS_VERSION` 7 / `FLIGHT_METRICS_VERSION` 3 (bumped from 6/2 with the SimConnect pitch/bank sign fix, so rotation rates and landing pitch of MSFS flights are recomputed): `flight_metrics_recent` refills the 200 newest completed flights in its background thread (facts and metrics together, `approach::store_facts`), `approach_facts_recent` computes what is still stale inline; older flights are assessed when opened (`approach_analysis` always runs with the current profile).
- **Per-flight metrics** (`crates/vectasim-store/src/metrics.rs`, frontend twin `flightMetrics` in `app/src/trackEvents.ts`): the derivation behind the track markers, ported 1:1. The thresholds live only in `app/src/trackEvents.constants.json` (the store embeds it with `include_str!`), and both test suites run the shared vectors `app/src/fixtures/track-metrics-vectors.json` (regenerate by hand, review `expected`). Written at flight end together with the approach facts (`approach::store_facts`, one track decode, one analysis; events `approach:facts` + `flight:metrics`). Older flights: `flight_metrics_recent` (window = the 200 newest completed flights, like `approach_facts_recent`) never computes inside the command – it returns what is stored plus `pending`, settles trackless flights at once and starts at most one background thread (`app/src-tauri/src/metrics.rs`) that works through the missing flights newest first with a 25 ms pause between flights and emits `flight:metrics` every 10 flights and at the end. The debrief sentences (`flightMetricLines` in `landing/history.ts`) compare against runway → type → all, widening to the next scope when fewer than `MIN_PEERS` flights have the value; trends get `rotation`, `gearDown`, `exceedances` series.
- **Map** (`app/src/map/`): the OpenFreeMap style is loaded once, patched per theme (`basemap.ts`) and cached; own layers: airports, airport diagram (OSM `aeroway`), track, planned route, VATSIM/IVAO traffic/ATC, METAR badges, own aircraft (silhouette by wake turbulence category). After a theme change, the custom 3D layers are removed first (so they free their GPU memory while the GL context is still alive), then the style is set again and the layers are recreated. The 3D curtain of a long track is rebuilt in chunks of 2000 points in the background; the nearest-airfield lookup for the height of 3D traffic uses a 0.25° grid (`map/traffic3d.ts`).
- **Online feeds: enabled vs. shown** (`crates/vectasim-online/src/feed.rs`, `app/src-tauri/src/online.rs`): *enabled* (settings `online_vatsim` / `online_ivao`, Settings → Display → Online traffic, `online_set_networks`) starts a network's poller at app start; disabling stops it and drops its snapshot and track history. *Shown on the map* (setting `online_shown`, the map's “Traffic” toggle and network choice, `online_set_shown`; missing – the toggle never used – = the enabled networks, as before the split) is purely visual: hiding never stops a feed, it only drops the poller to `BACKGROUND_POLL_INTERVAL` (60 s; also while the window is hidden, `set_ui_visible`), and showing wakes it back to 15 s. So the track history (`history.rs`, 2 h / 480 fixes, `GONE_MS` 3 min) is recorded from app start on and a clicked aircraft shows its flown path even right after the traffic was switched on. Showing a disabled network enables it (the map's opt-in). `online_snapshot_in_bbox` answers only from shown networks; while hidden the map neither queries nor draws traffic/ATC, `online:summary` keeps coming (`shown`, per network `shown` / `background` / `backgroundPollS`, also in the diagnostics package's `system.json` → `online`).
- **Map render budget** (`app/src/map/frameCap.ts`, binding for every new render loop): the simulator shares the PC and the GPU, so the map must not render at the display’s rate while it follows the aircraft. `capRenders(map, …)` wraps MapLibre’s `triggerRepaint`: every frame that is not part of a user gesture or a MapLibre camera animation (follow camera, model pose blends, traffic, the source updates of each sample) is at most `FRAME_MS_FOCUSED` apart (30 fps), `FRAME_MS_BACKGROUND` (15 fps) while another window has the focus, and nothing is drawn while `windowAway()` (document hidden, window minimised or in the tray). Gestures and MapLibre’s own camera animations keep the full rate. Follow steps under half a pixel and invisible model changes are not sent at all (`aircraftModel.poseChangeVisible`), and labels have no fade; while following, the map makes about 8 backend calls per second. A new animation loop schedules its next frame with `frameAfter(followFrameMs(), …)` (sleeps in a timer, then waits for the frame) and skips while `windowAway()`, instead of waking with `requestAnimationFrame` at the display rate. **The window state comes from Tauri:** WebView2 does not tell the page that the window is minimised (`document.hidden` stays false, `requestAnimationFrame` keeps running), so `watchWindow()` takes the focus from `onFocusChanged` and the minimised state from `isMinimized()` after every resize and focus change; `document.hasFocus()` / `document.hidden` are only the fallback (browser preview, tests). `onWindowReturn()` tells the map when the window may show again (left the minimised state, or got the focus back – a window restored from the tray is never minimised), and `capRenders` also redraws on `visibilitychange` (the tray does set `document.hidden`), so it draws at once and the camera glides back to the aircraft. A window that is only covered by another one gives no signal and renders at the unfocused rate.
- **Dialogs** (`app/src/ui/Modal.tsx`, rules in `ui/modalStack.ts`, binding for every new dialog): `useModal` / `<Modal>` provide the portal, the backdrop, `role="dialog"` + `aria-modal`, the focus trap (Tab/Shift+Tab wrap around), Esc for the topmost layer only, the shell and every lower dialog `inert`, focus back to the opener, the kept background scroll position and the reduced-motion fade. The modal stack is a counter, so stacked dialogs (debrief over the year-review lightbox) close in any order; while `isModalOpen()`, the global shortcuts (Ctrl+1…4, Ctrl+F, Ctrl+.) stay off. A dialog keeps its own class names and adds keys through `onKeyDown` (called first, only while it is on top) – never a focus trap or a window keydown listener of its own.
- **Themes** (`app/src/themes.ts`): token sets are written as CSS variables on `:root`; `theme.ts` provides the map colours live. Rule: no violet/magenta (tests check this), own aircraft always `#ffd54a`, text/surface contrast ≥ 4.5:1.
- **Events to the frontend:** `sim:status`, `sim:telemetry`, `sim:flight`, `sim:flight-event`, `sim:aircraft`, `sim:event`, `sim:stats`, `diag:raw`, `online:summary`, `logbook:changed`, `approach:facts`, `flight:metrics`, `approach:profiles`, `dispatch:ofp`, `theme:changed`.
- **Overlay & API** (`crates/vectasim-server`, app integration `app/src-tauri/src/server.rs`, docs [`docs/overlay-api.md`](docs/overlay-api.md)): off by default; its own thread with a single-threaded Tokio runtime, reads via the `Source` trait (manager snapshot, store, settings) in the blocking pool and polls at 2 Hz only while WebSocket clients are connected – nothing hangs in the live path. Events (`phase`, `landing`, `flightSaved`, `status`) are derived from consecutive snapshots (`watch.rs`). Settings `server_enabled`, `server_port`, `server_lan`, `server_token` in `settings`. Without the app: `cargo run -p vectasim-server --example demo [port] [--lan] [--privacy]`.
- **Connection limits** (`routes.rs`): separate pools for this PC and for other devices (64 HTTP each, 16 per device); an idle local connection gives way to a new local request, otherwise a local request waits at most 2 s and gets 503; every refused request closes its connection. WebSockets: 16 local plus 16 for other devices (4 per device). The token cookie is named after the port (`vectasim_token_<port>`); a cookie with an outdated token and the old port-less cookie are deleted (`Max-Age=0`) by the next answer, and the start page carries the token in `<meta name="vectasim-token">` only for a request that sent the valid token itself (query, header or cookie) while network access is on, so its OBS copy links work after a bookmark load; a token-free loopback request gets the empty element. An idle local connection that is asked to give way and has sent only part of a request head is dropped after 250 ms (`KICK_GRACE`).
- **Paths and hosts** (`data.rs`, `vectasim-xplane`): network paths (UNC) are refused for exports, imports, the landing card folder and the SimConnect.dll choice; the deny list sees the resolved path (8.3 names, trailing dots, junctions). An X-Plane host name is resolved on every connection and refused when it points only to public addresses. The opener’s `open-url` scope lists only the hosts the app links to; stored photo credit links that are not Planespotters pages are dropped on read.
- **Security of the local server** (`auth.rs`): without the LAN switch only `127.0.0.1`; with LAN `0.0.0.0` and a mandatory token (24 characters from OS randomness, constant-time comparison) for all non-loopback peers. One token per request, taken from `X-VectaSim-Token`, then `Authorization: Bearer`, then `?token=`, then the cookie `vectasim_token_<port>` (`request_token`, `cookie_name`; the first one present counts even if it is wrong, so a stale header beats a valid cookie and a new URL token beats an old cookie). A LAN request admitted by a valid `?token=` gets `Set-Cookie: vectasim_token_<port>=…; Path=/; Max-Age=31536000; HttpOnly; SameSite=Strict` (`routes.rs`; no `Secure`, the server speaks plain HTTP; the port is in the name because browsers send cookies to every port of an address), and `overlay/overlay.js` removes the token from the address bar with `history.replaceState` and keeps it in `sessionStorage` for the WebSocket URL and the start-page links – the token stays out of history and bookmarks. *Regenerate* replaces `server_token`; old links, headers and cookies then get 401, and a cookie with a token that is no longer valid (Regenerate, LAN access off) and the port-less `vectasim_token` of 0.5.1 are deleted by the next answer (`Max-Age=0`, `stale_cookies`). The start page carries the token in a `<meta>` element only for a request that presented the valid token itself while LAN access is on, so its copy URLs work when it was opened from a bookmark; plain loopback requests get the empty element (a local process cannot read the LAN token from the page). Token-free only with a loopback peer **and** a loopback `Host` (against DNS rebinding); `Origin` only own/loopback origin or OBS (`http://absolute`), otherwise 403 – also during the WebSocket handshake; only GET/HEAD/OPTIONS; strict CSP on the pages; streamer mode masks all responses like the UI. Tests: `crates/vectasim-server/src/{auth,api,routes,watch}.rs`, `tests/server.rs` (routing, token, masking, JSON golden, WS handshake, port in use).
- **Decoder / replay** (`crates/vectasim-simconnect/src/decoder.rs`, `replay.rs`): the interpretation of the SimConnect raw values (conversions, events → `ProviderEvent`, exception texts) is a `Decoder` without FFI and without a clock; the live `Session` and the `ReplayProvider` share it. Raw recording: `vectasim-dump::DumpRecorder` (see above).

### Export format `.vectasim` (full export, `crates/vectasim-store/src/bundle.rs`)

- ZIP; `manifest.json`: `format` (1), `app`, `appVersion`, `schemaVersion`, `createdMs`/`createdUtc`, counters (`flights`, `flightsDeleted`, `tracks`, `airframes`, `images`), `trackEncoding` (`vstk1`). A reader rejects a higher `format`; a newer schema is only a hint.
- `flights.jsonl`: one line per flight – `flight` (all columns of `flights` under their SQL name, including `deleted_ms`, plan, METAR and airframe fields), `touchdowns` and `phaseEvents` (rows without the local `id`/`flight_id`), `track` (`file`, `previewFile`, `sampleCount`, `encoding`, `updatedMs`).
- `tracks/<flight_id>.bin` and `tracks/<flight_id>.preview.bin`: the blobs raw as in the DB (zstd, codec as per `encoding`), stored uncompressed in the ZIP.
- `airframes.jsonl`: `airframe` (all columns of `airframes`) and `imageFile` for your own images; `images/<registration>.<ext>` (jpg/jpeg/png/webp/gif, ≤ 15 MB).
- Not included: `landing_facts`, `approach_facts` (cache, recalculated), settings; the app does not export demo/replay flights.
- Import: unknown columns are skipped, missing ones get their defaults; only the listed entries are read, with a size limit (no extraction by entry name). A flight in state `active` arrives as `interrupted`.
- Merge: same `id`, or same `dep_icao`/`arr_icao` with |Δ `off_block_ms`| < 15 min (trash included) = duplicate; airframes only fill empty fields, an image only if there is none; one transaction per 100 flights.
- Replace: first `create_backup(PreImport)` (`vectasim-pre-import-…`), then delete and insert in **one** transaction; no replace without a backup.

### SimConnect.dll (origin, updating)

The DLL is **not** in the repo and not in the installer (the installer only downloads it from Microsoft’s server on request, see below): the MSFS SDK EULA only allows redistribution of “distributable code” without naming SimConnect.dll as such; enquiries to Microsoft have gone unanswered. There is no Microsoft NuGet package.

Instead, `app/src-tauri/src/simconnect_dl.rs` (commands `simconnect_download_info`, `download_simconnect`, event `simconnect-download` with `{phase, received, total}`): on click, downloads the pinned ZIP of the MSFS 2020 SDK Core from `sdk.flightsimulator.com` via `%SystemRoot%\System32\curl.exe` (HTTPS only), checks size + SHA-256, takes out `cab1.cab`, extracts only the DLL with `expand.exe -F:<MSI file key>`, checks its SHA-256 and stores it as `%LOCALAPPDATA%\io.vectasim.app\simconnect\SimConnect.dll` (+ `SOURCE.txt`). The MSI is never run. According to Microsoft/Asobo, the 2020 DLL also works with MSFS 2024; the 2024 SDK ZIP would be ~620 MB.

The same download also runs without a window (for the installer, `app/src-tauri/windows/hooks.nsi`): `vectasim.exe --install-simconnect` is intercepted in `run()` **before** the Tauri builder (no single-instance handover, a running app is left alone). Exit codes: `0` DLL downloaded and verified or already present, `2` download failed/no network, `3` checksum mismatch, `1` otherwise. `--install-simconnect --check` downloads nothing: `0` if the loader would find a DLL (search order from `ffi::candidate_paths`; the downloaded one only counts with a matching SHA-256), otherwise `1` – the file chosen in *Settings → Simulator* is stored in the database and is not read here. Every call appends a line with a UTC timestamp (source, SHA-256, duration or error) to `%LOCALAPPDATA%\io.vectasim.app\logs\simconnect-install.log` and writes it to stderr (in the release build only visible when redirected: `vectasim.exe --install-simconnect 2> out.txt`). The installer only asks interactively (not with `/S` or `/P`, so also not during auto-update) and does not abort on an error.

Current: SDK Core **0.24.6.0**, ZIP 113 306 986 B, SHA-256 `6daaa1fa45598d890d17b1c8347cd736e529c83bfc00630fcefe8822500eaf3f`; DLL 67 072 B, SHA-256 `cffb74b62b596a897b0ff101bac3d66ea10236c540c75864658b451ffd1e6513`, MSI file key `filtEQeYbpLedi0MhYth1bxHyr8SqE` in `cab1.cab`.

Pinning a new SDK version:

1. Take the newest entry in `https://sdk.flightsimulator.com/files/sdk.json` (`game_versions[0].downloads_menu["SDK Installer (Core)"]`), download the ZIP into an empty folder, note the size and `sha256sum`.
2. Take the `.msi` out of the ZIP and read the `File`/`Media` tables (PowerShell, COM `WindowsInstaller.Installer`, `SELECT File, FileName, Sequence FROM File` and `SELECT DiskId, LastSequence, Cabinet FROM Media`): the key of the row `…|SimConnect.dll` with the 64-bit size in the `lib` folder (not `Microsoft.FlightSimulator.SimConnect.dll`), the cabinet from the sequence.
3. `expand.exe -F:<key> <cab> <out>` → DLL size and SHA-256; the PE machine must be `0x8664`.
4. Replace the constants at the top of `simconnect_dl.rs`, then `VECTASIM_TEST_SDK_ZIP=<zip> cargo test -p vectasim --lib simconnect_dl -- --ignored` (end-to-end extraction), and connect on the sim PC with 2020 and 2024.

### Airport index (precompiled)

The source remains `crates/vectasim-data/data/{airports,runways}.csv` (update with `python scripts/update-airports.py`). The crate’s `build.rs` translates them on every `cargo build` into `OUT_DIR/airports.vsad` (build artifact, not in the repo); `include_bytes!` embeds it. Format (`src/binfmt.rs`, little-endian):

1. Header: `VSAD`, version byte (`binfmt::VERSION`, bump on every layout change), counters (airports, runways, groups, grid entries, string table).
2. String table: all texts deduplicated back to back (UTF-8); fields refer to them with (offset u32, length u16).
3. Airports and runways as fixed-size records (57 / 90 bytes; coordinates as f64, missing values via bitmask) – random access without an offset table.
4. Runway groups per airport (start, count), sorted by ident; plus the airport permutation sorted by ident (binary search instead of a HashMap).
5. Dense 1° grid (181 × 361 cells) as prefix offsets + airport indices – bbox/nearest without setup work.
6. `load()` only checks the header, size and index arrays and decodes records on access (`OnceLock`); if the blob doesn’t fit (version, size, indices), the embedded CSVs are parsed (same result, ~230 ms). The test `precompiled_index_matches_csv` compares every record.

Load time (`cargo test -p vectasim-data --release -- --ignored --nocapture load_benchmark`): previously CSV parsing ~125 ms (release) / ~600 ms (debug), now ~2 ms / ~25 ms; the first world view query (`in_bbox` over everything, 500 hits) ~16 ms.

### Countries (embedded)

`crates/vectasim-data/data/countries.csv` (iso2, continent, German/English name; 249 ISO 3166 codes + `XK`) and `countries.geojson.zst` (Natural Earth 1:110m Admin-0, only the property `iso2`, coordinates rounded to 0.01°, zstd level 19: ≈ 165 KiB GeoJSON → ≈ 42 KiB) are generated by `python -I scripts/update-countries.py [download-dir]` (Python 3.14+ for the standard-library `compression.zstd`; no other packages). Special cases in the script: `ISO_A2` “-99”/“CN-TW” → `ISO_A2_EH` (France, Norway, Kosovo, Taiwan), Northern Cyprus → CY, Somaliland → SO (this is how OurAirports assigns their airports), French Guiana (GF) split out of France and Svalbard (SJ) out of Norway. Microstates without an outline at 1:110m (e.g. Singapore, Malta) appear on the map only via the airport dots, in the list as normal.

Counting (`vectasim_data::countries::visited_countries`, command `visited_countries` in `app/src-tauri/src/countries.rs`): `list_flights` (without trash) → `state = completed`, `arr_icao` set, provider `mock`/`replay` only with `include_demo` → `country` (OurAirports `iso_country`) of the arrival airport; date = `landing_ms`, otherwise `on_block_ms`. Unknown airports and codes outside the list (`ZZ`, `XP`) don’t count. The view loads the list and borders once (`countries_list`, `countries_geojson` as raw bytes) and the count again on `logbook:changed`.

### Filed route of online traffic (`crates/vectasim-route`)

The flight card's *Show route* (`map/TrafficCard.tsx`, drawing in `map/trafficRoute.ts`, layers `traffic-route-*` in `map/online.ts`) calls `traffic_route_resolve({ dep, arr, route })` (`app/src-tauri/src/online.rs`). The command answers from a per-session cache (`RouteCache`, key: departure, arrival, normalised route text, whether a SimConnect session can answer) or resolves in `spawn_blocking` and returns `{ points: [{ ident, lat, lon, source, resolved, gapBefore, airway? }], unresolved, total, resolvedCount, enroute, airwaysExpanded, sources }` (`source`: `msfs` | `xplane` | `navaids` | `airport` | `coord`). The frontend shows “resolving …” meanwhile, draws solid legs, dashed great-circle bridges where `gapBefore` is set (and the plain great circle when `enroute` is 0 or the command failed), dots from zoom 6 and idents from zoom 7, in the theme’s traffic colour.

- **Grammar** (`token.rs`): whitespace split, upper-cased; coordinates `50N008E`, `5020N00830E`, `5020N/00830E`, `502000N0083000E` are points; `X/…` keeps `X`; dropped: speed/level groups (`N0450F350`, `M082F370`, `K0850S1130`), bare levels, `DCT`, `DIRECT`, `VFR`, `IFR`, `OAT`, `GAT`, `IFPSTOP`, `IFPSTART`, `SID`, `STAR`, `STAY…`, `C/…`, tokens with other characters, shorter than 2 or longer than 12, and the departure/arrival repeated at the ends. An airway-shaped token (1–3 letters, 1–4 digits, optional letter) after a point is an airway; anywhere else a point.
- **Candidates** (`lib.rs`): sources in priority order MSFS → X-Plane → bundled (OurAirports navaids, 4-letter idents from the airport index); the first source with a candidate within `MAX_LEG_NM` (1 500 nm) of the previous resolved point (the departure for the first) wins, nearest candidate of that source. An airway between two resolved points is expanded by the first source that knows it (MSFS, then X-Plane), else joined directly – unless the token resolves as a fix lying roughly on the way (terminal fixes like `DF432`). An unresolved point right after the departure or right before the arrival is taken for a SID/STAR and skipped; other unresolved points are listed and set `gapBefore` on the next point. `total`/`resolvedCount` count departure, arrival and the filed points, not inserted airway fixes.
- **MSFS** (`msfs.rs`, `crates/vectasim-simconnect/src/facility.rs`): `SimConnect_AddToFacilityDefinition`, `SimConnect_RequestFacilityData` and `_EX1` (type byte `W`/`V`/`N`, MSFS 2024) are optional DLL exports like `SimConnect_Text`. The app queues `FacilityQuery`s in the process-wide `FacilityBroker` and blocks in `lookup` (timeout 3 s per batch, 12 s per resolution); the SimConnect session registers four facility definitions once (AIRPORT/VOR/NDB: position; WAYPOINT: position, region and the ROUTE children `NAME`, `NEXT_*`/`PREV_*` ICAO, region, latitude, longitude), sends the queued requests from its pump over its own handle and answers them from its dispatch loop (`FACILITY_DATA`, `FACILITY_DATA_END`, `FACILITY_MINIMAL_LIST` for an ident in several regions; exceptions on a request = not found). While a lookup waits, the idle wait drops from 100 to 5 ms. Message ids are accepted in both numberings (29/30/31 per the 2024 SDK, 28/29/30 without the experimental `PICK` entry) and the payload at offset 40 or 37 (the SDK documents `IsListItem` as a one-byte `bool`) – both told apart by the known payload size. No session, no exports, a rejected definition (exception or HRESULT) or no answer in time: the source is skipped. Airways are walked fix by fix along the ROUTE children in the direction that gets closer to the exit fix (≤ 150 fixes). Facility messages are not written to the raw dump. Tests: `facility.rs` (decoder, broker), `tests.rs` (session with a fake backend), `vectasim-route/src/tests.rs` (stand-in session).
- **X-Plane** (`xplane.rs`): install folders from `%LOCALAPPDATA%\x-plane_install_12.txt`, then `_11.txt` (one path per line, existing folders only); per file `Custom Data\` before `Resources\default data\`; the first install with a fix or nav file is used. `earth_fix.dat` (1101/1200, 600), `earth_nav.dat` (rows 2 = NDB, 3 = VOR; 1150/1200, 810) and `earth_awy.dat` (1100 by ident/region/type, 640 with coordinates) are parsed once on a background thread on first use (`XPlaneNav`, callers wait ≤ 20 s; a result produced while it is still parsing is not cached), at most 3 M lines and 512 MB per file, into ident → candidates and airway → segments (breadth-first search between the nodes nearest to the resolved end points, ≤ 30 nm). The files are only read. Fixtures in `crates/vectasim-route/tests/fixtures/xplane/`.
- **Bundled** (`vectasim_data::navaids`): `data/navaids.csv.zst` from `python -I scripts/update-navaids.py` (OurAirports, public domain; ident, name, type, position, frequency, country; sorted by ident, binary search).

### Performance (background, SimConnect)

- **Hidden window:** the frontend reports `invoke("set_ui_visible", { visible })` when the window is hidden, minimised or sent to the tray (`app/src/uiVisibility.ts`). Visible = document shown **and** window not minimised; because WebView2 never fires `visibilitychange` on minimise, Tauri’s `isMinimized()` after every resize decides as well, and `visibilitychange` stays the fallback (tray hide, browser preview). Focus is not the signal – an unfocused window beside the sim is still visible. This works without the tray icon too. While hidden: `sim:telemetry` (and the periodic `sim:flight`) at 1 Hz, `sim:stats` at 0.2 Hz, `diag:raw` off, the online feeds at their 60 s background rate; event-driven events (`sim:status`, `sim:flight-event`, `sim:aircraft`, `logbook:changed`) and `FlightSession`/recorder keep running unchanged on the full stream.
- **Images to disk:** `save_image` (landing, approach, year-review and country images) takes the PNG as the raw IPC body (`Uint8Array`, `app/src/saveImage.ts`) with the target path percent-encoded in a header, instead of a JSON array of numbers – large images and *Save all* no longer stall the webview. The path goes through `data::check_path` like every other write.
- **Incremental live track:** `invoke("get_live_track_since", { tsMs })` returns only samples with `t_ms > tsMs`; after `flightStarted` or a provider change, start again with `get_live_track` (the buffer is then replaced or cleared).
- **SimConnect pump:** `SimConnect_Open` gets an auto-reset event (`CreateEventW`); with an empty queue the thread waits with `WaitForSingleObject` for at most 100 ms (stop flag and watchdog stay effective) instead of polling every 2 ms. Without an event (creation failed), the old polling remains.

## Security

How to report a vulnerability: [SECURITY.md](SECURITY.md) (private report through GitHub, no public issue).

**Content Security Policy** (`app/src-tauri/tauri.conf.json` → `app.security.csp`). It applies to the built webview; `tauri dev` loads the Vite server directly and runs without CSP on the desktop – CSP problems therefore only show up in `npm run tauri build` (or the installer). Network requests from Rust (reqwest: METAR, VATSIM, IVAO, SimBrief, Planespotters API, updater) are not subject to the CSP and are therefore deliberately **not** listed in it. Sources:

| Directive | Source | What for |
|---|---|---|
| `default-src` | `'self'` | everything not listed only from the app bundle |
| `script-src` | `'self'` | bundled JS; Tauri adds hashes for its own inline scripts itself. No `'unsafe-eval'`: MapLibre GL 6 doesn’t need it |
| `style-src` | `'self' 'unsafe-inline'` | Vite CSS bundle. `'unsafe-inline'` is a safeguard for `style` attributes in HTML strings (MapLibre popups via `setHTML`, libraries that use `setAttribute("style")`); React and MapLibre styles via the CSSOM are allowed anyway. `dangerousDisableAssetCspModification: ["style-src"]` prevents Tauri from appending nonces – with a nonce, the browser would ignore `'unsafe-inline'` |
| `img-src` | `'self' asset: http://asset.localhost` | your own aircraft images via the asset protocol (`convertFileSrc`, scope restricted at runtime to the app’s image folder, `airframes.rs`) |
| | `data: blob:` | SVG icons on the map (`aircraftIcons.ts`), landing card as PNG (`exportCard.ts`), MapLibre rasters from blobs |
| | `https://tiles.openfreemap.org` | Natural Earth raster tiles of the basemap style |
| | `https://tiles.maps.eox.at` | satellite imagery (`map/satellite.ts`; MapLibre loads rasters via fetch, so it is in `connect-src` too) |
| | `https://*.plnspttrs.net https://*.planespotters.net` | Planespotters photos (hotlink, thumbnails on `t.plnspttrs.net`) |
| `font-src` | `'self' data:` | bundled `@fontsource` fonts |
| `connect-src` | `'self' ipc: http://ipc.localhost` | Tauri IPC (commands, events) |

| | `https://api.rainviewer.com https://tilecache.rainviewer.com https://view.eumetsat.int` | weather overlay (`map/weatherOverlay.ts`): radar index and tiles, cloud WMS and its capabilities – fetched by the `vectasim-radar://` / `vectasim-clouds://` MapLibre protocols, only while that layer is on |

New remote content in the webview (e.g. another map provider) needs an entry here and in the table.

**MapLibre GL JS** is on 6.x (from 6.12.0): 5.x had [GHSA-jrc7-96c5-q579](https://github.com/advisories/GHSA-jrc7-96c5-q579) (XSS bypass in `DOM.sanitize`). The popups (`app/src/map/online.ts`) still escape all values themselves (`esc`) before they go through `setHTML` – never put feed data (VATSIM, IVAO, METAR) unescaped into HTML strings. CI checks the production dependencies with `npm audit --omit=dev --audit-level=high` (high/critical fail the job). MapLibre 6 is ESM-only (`import * as maplibregl`), loads the worker via `setWorkerUrl` (see above) and no longer ships the global `GeoJSON` namespace (`app/src/map/geojson.d.ts`).

**Paths from the webview** (`data::check_path`): `save_export`, `export_logbook_csv`, `save_image`, `export_bundle` and `create_diag_package` only write to paths that are absolute, contain no `..`, have the matching extension (format extension `.csv/.gpx/.kml/.json`, `.png`, `.vectasim`, `.zip`) and are not under `%WINDIR%`, the program folders (`ProgramFiles`, `ProgramFiles(x86)`, `ProgramW6432`) or the app’s installation folder – otherwise the error “path not allowed”. `import_bundle`/`read_bundle_manifest` check absolute, no `..`, extension `.vectasim`.

**Exports:** free-text cells in the logbook CSV (aircraft title, callsign, ICAO, provider …) that start with `=`, `+`, `-`, `@`, tab or CR get a `'` prefix (CSV/formula injection); number cells stay unchanged (`export.rs`). **Track blobs** are treated as untrusted: at most 200 000 samples, the sample count in the header must match the blob length, and decompression is bounded – a broken entry returns an error instead of running out of memory (`track.rs`).

## Conventions

- Comments give the reason, not where it came from: no finding IDs from reviews, no planning phases, and menu paths in the English UI wording (*Settings → Diagnostics*). The publishing check refuses review IDs.
- Rust: doc comments explain the *why*; `unsafe` only in the SimConnect FFI with a `SAFETY` comment; Clippy without warnings.
- Frontend: serde fields camelCase, types mirrored in `app/src/types.ts`; UI texts through i18n (German reference, English second – see “Languages” below), flight phases in English; numbers via `format.ts` / `i18n/number.ts` (UTC with “z”, thousands separators, a real minus sign).
- No new dependencies without a reason; charts are hand-written SVG.
- **Languages of the project:** the app is bilingual German/English; the public documentation (README, `docs/installation.md`, `docs/overlay-api.md`, `docs/releasing.md`, `docs/sim-pc-checklist.md`, `docs/approach-profiles.md`, `docs/approach-profiles-sources.md`, `docs/brand/README.md`, `app/README.md`, `THIRD-PARTY-NOTICES.md`, script comments, this file, `CHANGELOG.md`) is written in English; `README.de.md` is the German twin of the README.
- **README pairs:** [README.md](README.md) (English) and [README.de.md](README.de.md) (German) list the same features and are updated together on every feature change – same sections, same feature list (checked by `scripts/readme-pair-check.mjs`, see *Tests and checks*).
- **CHANGELOG:** new entries in English under `## Unreleased`, one bullet per user-visible change (a bullet may group closely related fixes), written for users: what changed and what they notice. Implementation details – environment variables, algorithms, file formats, schema versions, crate versions, WebView2/Tauri internals – belong in this file or in the commit message. When a later commit changes the same feature again, rewrite its bullet instead of adding a second one.

## Languages (i18n)

German is the reference language, English the second one. An own lean solution without dependencies in `app/src/i18n/` (bundled JSON resources; keys typed from `de/*.json` – one file per area, merged in `de/index.ts`; plurals via `Intl.PluralRules`, number format as in `format.ts`). The language follows the setting `language` and switches live (no reload). All views are migrated; `npm run i18n:extract` lists the few remaining literals (mostly German fallbacks behind getters, e.g. theme moods in `themes.ts`).

- **Usage:** in components `const t = useT();` → `t("nav.map")`; outside React (toasts, `errors.ts`, stores) `import { t } from "./i18n"`. `I18nProvider` sits in `main.tsx`; `<I18nProvider lang="en">` pins a subtree to one language (preview, tests).
- **Label tables and constant strings (live binding):** module-level lookups must not freeze the language at import time. Tables such as `BAND_LABEL`, `APPROACH_BAND_LABEL`, `LATERAL_BAND_LABEL` (`landing/facts.ts`, helper `labels(keys, k => t(…))`) are plain `Record`s whose properties are getters that call `t()` on every access; theme names/moods in `themes.ts` work the same way. Exported constant sentences (`VS_BANDS`, `G_BANDS`, `LATERAL_REASON` …) are `export let` and rebuilt by a `refreshStrings()` registered with `subscribeLanguage` – importers see the new value through the ES module live binding. Never copy such a value into a module constant.
- **Markup inside sentences:** `rich(text, { name: <code>…</code> })` (`app/src/ui/richText.tsx`) inserts React nodes for the `{name}` placeholders that `t()` left untouched, so a sentence with `<code>`, `<b>` or a link stays one key.
- **Exports in a fixed language:** `tIn(lang, key, vars)` translates in an explicit language (landing/approach card PNG, countries and year-in-review images, file names such as `VectaSim_Approach_…`/`VectaSim_Anflug_…`); render functions take `lang` as a parameter instead of reading the global.
- **Language:** setting `language` = `de` | `en` | `system` (default `system` = Windows display language via `navigator.language`; neither de nor en → de). Stored like all prefs in the `settings` table; `prefs.ts` passes it on to `i18n/lang.ts`.
- **Keys and namespaces:** nested JSON, key = dot path. One namespace per area or file in camelCase (`nav`, `band`, `logbook`, `flightDetail`, `settings.display` …); leaves describe the meaning, not the text (`logbook.deleteConfirm`, not `logbook.endgueltigLoeschen`). Recurring words in `common.*`. `de/*.json` (one file per area, merged in `de/index.ts`) is the reference: new keys always go there first, then into `en/*.json`. Keys are typed from `de.json` (`TKey`) – a typo is a tsc error.
- **Placeholders:** `{name}`; numbers are inserted language-appropriately without decimals (`1 500` / `1,500`); format anything with a unit or decimals beforehand with `i18n/number` and pass it as a string. Whole sentences as one key – don’t glue sentence fragments together, the word order differs.
- **Plurals:** object `{ "one": "{count} Flug", "other": "{count} Flüge" }` (categories of `Intl.PluralRules`, `other` mandatory); call `t("count.flights", { count })` – without `count`, tsc reports an error.
- **Numbers, dates, times:** `app/src/i18n/number.ts` has the same functions as `format.ts` (`fmt`, `fmtNum`, `fmtSigned`, `fmtDuration`, `fmtWeight`, `fmtDate`, …) with an optional `lang` at the end; for German the output is identical (golden tests). de: `1 500 ft`, `−155 fpm`, `1,25`, `17.10.2026`; en: `1,500 ft`, `-155 fpm`, `1.25`, `17 Oct 2026`. Times in 24 h, UTC with `z` or local time as before (`time_local`).
- **English style:** British spelling (centre, colour, normalised, minimise), matching the existing `en/*.json`; aviation terms as pilots use them (landing rate, touchdown zone, go-around, off-block/on-block, block time, air time, stable approach).
- **Not translated:** flight phases stay in English (`format.ts → PHASE_LABEL`), as do ICAO/METAR abbreviations, `FL350`, units (`ft`, `kt`, `fpm`, `g`), product names and the theme names.
- **Fallback:** if a key is missing in `en/*.json`, the German text appears (with a console warning in the dev build); if it is missing there too, the key.
- **Tests:** Vitest runs with `navigator.language` = `en-US`, so `system` resolves to English. Tests that assert German text pin the language with `beforeEach(() => setLanguageSetting("de"))` (or wrap in `<I18nProvider lang="de">`); English assertions pin `"en"` the same way.
- **Checking:** `npm run i18n:check` (in `app/`) reports missing/surplus keys between the languages, wrong plural forms, differing placeholders, empty texts and `t("…")` calls with an unknown key; exit code 1 on errors. `npm run i18n:extract` lists texts not yet migrated per file (`-- --file Fleet --all`, `-- --json`), read-only.
- **Rust texts** (notifications, tray, Discord, dialogs, overlay): read the setting `language` from the store (`system` → Windows UI language) and pick the text with a `match` on the language; no language parameter threaded through every call. Errors that end up in the frontend should preferably be delivered as code + detail and only be turned into user text in `errors.ts` with `t()`. The installer (NSIS) is already bilingual (`app/src-tauri/windows/hooks.nsi`).
- **Rust language (mechanics):** `vectasim_core::Lang` (`De`/`En`, `tr(de, en)`, `decimal`, `parse`, `from_locale`) is the shared type. `app/src-tauri/src/lang.rs` resolves `language` at startup (`lang::init` after opening the logbook) and on every `set_setting("language", …)` (`apply_setting`, then `tray::relabel`) and caches the result in an atomic: `lang::current()`, `lang::tr("…", "…")`, `trf!("… {x}", "… {x}")` (format! per language). `system`/unknown → `GetUserDefaultUILanguage` (kernel32, no crate), neither de nor en → de; before `init` the system language applies, in `cfg(test)` always de. Text functions take the language as a parameter (`notify::landing_text(lang, …)`, `tray::tooltip(lang, …)`, `PresenceInput.lang`) – testable without global state. The overlay server asks `Source::lang()` (page default, `Status.lang`, `bandLabel`, port errors).
- **Error codes (store):** rejections are `StoreError::Invalid(Invalid::…)` (`crates/vectasim-store/src/error.rs`) with a stable code `store.<snake_case>`, typed parameters (`params()`, camelCase keys, nested cause under `cause`) and text in both languages (`message(lang)`); `Display` = German text (reference, log). Technical errors: `store.sqlite|io|json|track` with an English `detail`, plus `store.newer_schema`, `store.migration_failed`, `store.backup_failed` (`step`). `to_json(lang)` returns `{ code, params, message }`. The Tauri commands still return `Err(String)` = `lang::ui_error(e)` (store errors in the backend language, everything else `Display`), because many components display `String(e)`; switching to a structured error object only works together with `errors.ts`/`rawText`. New rejection: variant in `Invalid` + code + both texts + parameters, golden test in `error.rs`.
- **Store texts:** the store has no global language. User-facing texts (import warnings, row errors, generated note lines) use `ltr!(lang, "de …", "en …", args…)` (`crates/vectasim-store/src/lib.rs`, `format!` per language); the language arrives as a field set by the app, not by the frontend: `ImportOptions.lang` (`.vectasim` import, `bundle.rs`) and `CsvImportOptions.lang` (`#[serde(skip)]`, `csvimport.rs`).

**UX conventions from the review fixes (map overlays):** a card on the map (traffic flight card, `.traffic-card`) must not cover what it describes – `measureInsets()` in `map/LiveMap.tsx` measures the free area beside the card and above the HUD, camera moves use it as `offset` (`insetOffset`) or as `padding` for `cameraForBounds`, and `pointFree()` checks whether a point is visible. Colours drawn on the basemap go through `ensureContrast(color, ground, ink, min)` in `map/aircraftIcons.ts` (mixes towards the text colour in 5 % steps until WCAG contrast is reached: 4.5:1 for callsigns, 3:1 for symbols) so light themes stay readable.
